# Обоснование ограничений

## Как заполнять

- **CHECK, UNIQUE, FK** — обосновывать обязательно. Ссылка на `BR-N.M` + краткое «почему».
- **NOT NULL** — обосновывать **только** когда бизнес явно требует. Очевидные случаи (PK, FK на NOT NULL поле, поля из BR с явным «обязательно») — не дублировать.
- **NULL** (где разрешено) — обосновывать, потому что это осознанное решение, а не забывчивость.
- **DEFAULT, GENERATED** — кратко, если не очевидно.

**Правило:** если не можешь указать `BR-N.M` — либо ограничение лишнее, либо пропущено бизнес-правило. Разберись, прежде чем оставлять.

**Формат обоснования:** «<что ограничиваем> — потому что <BR-N.M> требует <что>».

Пример хорошего обоснования:

> `CHECK (rating BETWEEN 0 AND 5)` на `restaurant.rating` — потому что BR-4.2 задаёт диапазон рейтинга.

> `UNIQUE (address_id)` на `restaurant` — потому что BR-3.3 запрещает двум ресторанам делить один адрес.

> `FK (restaurant_id) → restaurant(restaurant_id)` на `product` — потому что BR-5.1 требует, чтобы блюдо принадлежало ресторану.

Пример плохого обоснования (не принимается):

> `NOT NULL` на `name` — потому что имя должно быть.

> `CHECK` на `price` — потому что цена не может быть отрицательной.

(Второе — обоснование «здравым смыслом», а не ссылкой на BR. Не принимается.)

## Ловушки

Здесь — не готовые решения, а **фиксация того, как ты решил** каждую ловушку. Преподаватель читает, чтобы понять ход мысли.

### Ловушка 1: `payment` — неполная сущность

**Какие атрибуты добавил в `payment` и почему** (BR-8.2):

```
В ERD у payment только payment_id и order_id. По BR-8.2 добавлены:
- pay_type payment_type          - тип оплаты попытки
- amount numeric(12,2)           - сумма попытки (BR-8.4)
- transaction_id varchar(64)     - внешний идентификатор транзакции от провайдера по BR-8.3, UNIQUE
- payment_timestamp timestamp    - дата и время транзакции
- status payment_status          - статус попытки

transaction_id имеет тип varchar, а не uuid: по BR-8.3 это внешний идентификатор,
он приходит от платёжного провайдера, а не генерируется нами, и его формат нам
не подконтролен. BR-11.1 про uuid относится к идентификаторам сущностей схемы,
которые генерируются на сервере через exts.uuid_generate_v4().
Данные карт не хранятся по BR-1.7, BR-8.5
```

**Где хранится тип оплаты — `payment` или `order`** (BR-8.6):

```
В payment (payment.pay_type). BR-8.6 прямо относит тип оплаты к попытке:
у одного заказа могут быть попытки с разными типами. В "order" хранится только
агрегированный статус оплаты pay_status по BR-7.8, BR-8.7
```

### Ловушка 2: `order.address_id` — принадлежность клиенту (BR-7.4)

**Как обеспечено, что адрес доставки принадлежит клиенту:**

```
Составной FK:
    foreign key (client_id, address_id)
        references client_address (client_id, address_id)

Цель FK — первичный ключ client_address. Заказ нельзя создать с парой
клиент, адрес, которой нет в client_address, то есть на чужой адрес.
Проверяется на уровне схемы, без триггера
```

### Ловушка 3: `order_structure` — один ресторан в заказе (BR-7.3)

**Как обеспечено, что все блюда из `order.restaurant_id`:**

```
На уровне приложения и генератора, в схеме отдельного ограничения нет.

Почему не составной FK: для него в order_structure пришлось бы добавить restaurant_id.
Этот столбец зависел бы только от order_id, то есть от части составного PK
order_id + product_id, - частичная зависимость, нарушение 2НФ

Почему не триггер: триггер на order_structure не закрывает смену restaurant_id
у заказа или блюда

В insert_test_data правило выполняется по построению - блюдо i принадлежит ресторану
(i-1)%value+1, заказ выбирает блюда только по индексам своего ресторана
```

### Ловушка 4: `review` — полиморфизм (BR-9.1)

**Как реализована валидность `review.entity_id`:**

```
Полиморфизм, как в ERD: пара (entity_type, entity_id). FK на entity_id нет -
столбец ссылается то на product, то на restaurant, то на "order", а внешний
ключ может указывать только на одну таблицу

Схема гарантирует:
- FK (order_id, client_id) - "order": отзыв только на свой заказ по BR-9.2
- UNIQUE (order_id, entity_type, entity_id): один отзыв на объект в заказе по BR-9.5

Существование entity_id проверяет генератор: отзыв ставится только на сам заказ,
его ресторан или его блюда.

Разбивать review на три таблицы не стал: триггер rating_change по FOOD-105
по контракту работает именно с парой entity_type + entity_id
```

## NOT NULL (только бизнес-обязательные)

Сюда — **только** те `NOT NULL`, которые нельзя объяснить очевидностью.

**Не дублируй:**
- PK (всегда NOT NULL по определению);
- FK на NOT NULL поле (очевидно, если родитель NOT NULL);
- поля из BR с явным «обязательно» — только если хочешь подчеркнуть, что это не случайность.

## Нормализация (3НФ)

Короткое обоснование, что все таблицы в 3НФ:

```
1НФ: все поля атомарны. Адрес разбит на улицу, дом и квартиру (BR-3.1),
позиции заказа вынесены в order_structure.

2НФ: составные PK в client_address, order_structure и courier_pay.
Неключевые поля зависят от ключа целиком: quantity - от пары заказ, блюдо,
сумма выплаты - от тройки год, месяц, курьер. Из-за этого в order_structure
нет restaurant_id: он зависел бы только от order_id

3НФ: транзитивных зависимостей нет. Категория блюда и адрес вынесены
в отдельные таблицы
```


**Имя таблицы заказов по BR-13.1.** Таблица называется `"order"` в двойных кавычках, без переименования: так имя совпадает с ERD и с запросами в протоколе проверки

**Технические параметры по BR-11.6.**

| Что | Тип | Почему                                          |
|---|---|-------------------------------------------------|
| Телефоны | `char(12)` | Формат `+7` и 10 цифр - ровно 12 символов       |
| `client.password` | `char(32)` | BR-2.3: MD5-хэш, всегда 32 hex-символа          |
| Денежные суммы | `numeric(12,2)`, цена `numeric(10,2)` | Рубли с копейками                               |
| `order_structure.quantity` | `numeric(8,3)` | BR-7.15: количество может быть дробным (0.5 кг) |
| Агрегированные рейтинги | `numeric(3,2)` | Среднее от 0 до 5 с двумя знаками               |
| `review.rating` | `numeric(2,1)` | Как в ERD (numeric); диапазон 1–5 по BR-9.4     |
| Коэффициенты | `numeric(2,1)` | Значения 0.1-0.5 с шагом 0.1                    |
| Даты и время | `timestamp`, `date`, `time` без часового пояса | BR-11.2: всё в часовом поясе сервера            |

Некоторые правила схема проверить не может - их держит insert_test_data и приложение:

- BR-7.10, order_amount = стоимость блюд. Это сумма по строкам другой таблицы
  CHECK так не умеет. insert_test_data считает её как сумму price * quantity
- BR-7.14, в заказе минимум одна позиция. "Хотя бы одна дочерняя строка"
  ограничением не выразить. insert_test_data кладёт от 1 до 5 позиций
- BR-8.4, сумма попытки = total_amount заказа. FK на вычисляемый столбец
  сломался бы при изменении суммы заказа. insert_test_data вставляет amount = total_amount
- BR-8.7, pay_status заказа соответствует попыткам. Тоже агрегат по другой таблице
  В insert_test_data: 'оплачен' - попытка 'успех', 'ошибка' - 'ошибка',
  'ожидает' - 'в_обработке'.
- BR-6.6, хотя бы один активный курьер. BR сам говорит, что на уровне схемы
